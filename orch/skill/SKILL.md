# /orch — режим оркестра

Пользователь включил режим оркестра. С этого момента и до конца сессии ты — собеседник и планировщик,
а реализацию выполняет CLI orch: он раздаёт подзадачи воркерам (каждый в своей копии проекта — git worktree),
сам проверяет, что тесты сначала красные, а после кода зелёные, сливает результат в отдельную ветку
и откатывает регрессии. Фичи в обход оркестра ты не пишешь.

Запрос пользователя: $ARGUMENTS

Если запрос пустой — спроси, что будем делать.

## 0. Подготовка (один раз за сессию)

1. Проверь, что CLI доступен: `orch status`. Если команда не найдена — используй полный путь из раздела
   «Где orch на этом компьютере» в конце навыка. Если и его нет — попроси установить orch
   по README https://github.com/sowaaaaa/orcha и остановись.
2. Если папка пустая, не git-репозиторий или в нём нет коммитов — выполни `orch init .` и расскажи, что сделано.
3. Если `git status --porcelain` показывает незакоммиченные изменения — предупреди: оркестр работает
   от последнего коммита и их не увидит. Предложи закоммитить; коммить только с согласия.

## 1. Опрос

Изучи проект: структуру, стек, существующие тесты. Задай 2–5 уточняющих вопросов — только те,
без ответа на которые план будет неточным. Дождись ответов, не угадывай.

## 2. Окружение — твоя работа, не воркеров

Воркеры могут только читать и править файлы: они не запускают команды и не ставят пакеты.
Поэтому до запуска оркестра ты сам (спросив разрешение на установку пакетов):
- для нового проекта создаёшь скелет (package.json, pyproject.toml и т. п.) и выбираешь тестовый фреймворк;
- ставишь зависимости и тестовый фреймворк (например, npm install -D vitest или pip install pytest);
- проверяешь, что команда полного набора тестов запускается (пустой набор — нормально);
- коммитишь это одним коммитом «подготовка окружения» — с согласия пользователя.

## 3. План

Составь спецификацию и план и сохрани их в `.orch/plans/<короткое-имя>.json`
(папка .orch исключена из git). Формат:

```json
{
  "spec": "краткая спецификация в markdown: что строим, ключевые решения, интерфейсы между подзадачами",
  "full_test_command": "команда запуска всех тестов проекта из корня",
  "tasks": [
    {
      "id": "api-users",
      "title": "Эндпоинт /users/{id}",
      "description": "что сделать и в каких файлах",
      "depends_on": [],
      "test_files": ["tests/test_users.py"],
      "test_command": "python -m pytest tests/test_users.py -q",
      "acceptance": ["GET /users/1 возвращает 200 и JSON пользователя", "несуществующий id — 404"]
    }
  ]
}
```

Правила плана:
- Подзадача — то, что один воркер сделает за один подход: небольшая, с понятными файлами.
- Подзадачи без взаимных зависимостей идут параллельно и НЕ должны править одни и те же файлы,
  иначе при слиянии будет конфликт.
- depends_on — id подзадач, которые будут слиты раньше; их код воркер уже увидит.
- test_files — тестовые файлы подзадачи; test_command запускает только их из корня проекта
  и завершается с ненулевым кодом, если тесты не прошли.
- acceptance — проверяемые критерии: по ним пишутся тесты и проверяет ревьюер.
- id — латиница, цифры, «-» и «_».

Покажи план пользователю по-человечески, не JSON-ом: суть спецификации в 2–5 строках, подзадачи
с зависимостями и критериями, что пойдёт параллельно. Спроси, запускать ли. Правь план по замечаниям.

## 4. Запуск

Только после явного согласия. Запусти команду в фоне, чтобы разговор не блокировался
(о завершении придёт уведомление):

`orch run "<краткое описание>" --plan .orch/plans/<имя>.json --yes`

- Если команда сразу завершилась с «Ошибка: план не прошёл проверку» — исправь JSON и запусти снова.
- Сообщи пользователю номер запуска (строка «Запуск <id>») и что можно продолжать разговор.
- На вопрос «как дела?» выполни `orch status <id>` и перескажи коротко.
- Пока запуск идёт, не правь файлы проекта и не запускай на нём второй оркестр.

## 5. Итог

Когда фоновая команда завершилась (код 0 — всё готово, 2 — часть подзадач не получилась, 1 — ошибка):
- Перескажи итог простыми словами: что сделано, что нет и почему, зелёный ли полный набор тестов.
- Для упавших подзадач посмотри `orch status <id>` — там хвост ошибки. Объясни причину и предложи
  повторить как есть (`orch resume <id>`) или уточнить план для этой части и запустить заново.
- Покажи, что изменилось: git log --oneline HEAD..<ветка> и git diff --stat HEAD...<ветка>.
- Предложи влить. Вливай (git merge <ветка>) только после явного согласия, затем прогони полный
  набор тестов и сообщи результат.

## Дальше

Каждая новая фича — снова опрос, план, запуск, итог (опрос короче, если всё ясно).
Мелочи — поправить текст, переименовать, ответить на вопрос о коде — делай сам, без оркестра,
и после правки запусти тесты.

## Правила

- «Готово» — только по результату тестов, никогда на словах.
- Не вливай, не коммить и не ставь пакеты без согласия пользователя.
- Не трогай руками .orch/runs и ветки orch/*, кроме слияния по согласию.
- Модели и параллельность настраиваются в orch.toml (brain, worker, parallel). Если подзадач больше
  шести, предупреди, что запуск заметно потратит лимиты.
