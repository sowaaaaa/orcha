# orch — спецификация

Оркестратор разработки по схеме: **опрос → план → тесты до кода → код до зелёного → ревью → слияние**.
Каждая подзадача выполняется в своём `git worktree`, независимые подзадачи идут параллельно.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Дирижёр | Python-код `orch` (без ИИ) | ведёт процесс, создаёт worktree, **сам** запускает тесты, решает «красное/зелёное», сливает ветки, откатывает регрессии |
| Мозг | модель `brain` (по умолчанию `claude-fable-5-1`) | опрос, спецификация + план, ревью результата. Только чтение файлов |
| Воркер | модель `worker` (по умолчанию `claude-opus-5-5`) | пишет тесты, затем код, в своей копии проекта. Может только читать/править файлы, команды запускать не может |

Модели вызываются через `claude -p --restricted` (Claude Code в фоновом режиме, аккаунт пользователя).
`--restricted` отключает пользовательские хуки и настройки и запрещает запуск команд.

## Процесс `orch run "задача"`

1. **Опрос.** Мозг читает проект и возвращает `{"questions": [...]}`; пользователь отвечает.
2. **План.** Мозг возвращает JSON `{spec, full_test_command, tasks[]}`; у задачи: `id, title, description,
   depends_on, test_files, test_command, acceptance`. Невалидный план → одна повторная попытка с текстом ошибки, потом отказ.
   Пользователь подтверждает план (или `--yes`).
3. Создаётся интеграционная ветка `orch/<run>/main` (от HEAD пользователя) в своём worktree.
   Ветка пользователя не меняется.
4. Для каждой готовой задачи (все зависимости слиты) — worktree `orch/<run>/<id>` от текущего HEAD интеграционной ветки:
   1. **Тесты.** Воркер пишет тесты. Дирижёр проверяет: тестовые файлы созданы/изменены и `test_command` **падает**.
      Тесты, зелёные без реализации, отклоняются. Лимит: `max_test_attempts`. Провал → `red_gate`.
      Принятые тесты коммитятся.
   2. **Код.** Воркер пишет реализацию. Дирижёр: если тестовые файлы изменены → откатить их, попытка не засчитана как успех;
      запустить `test_command`; красные → вывод ошибки уходит воркеру. Слова воркера («готово») не учитываются.
   3. **Ревью.** На зелёных тестах мозг сверяет diff с `acceptance`: `{"approved", "issues"}`.
      Отклонение → замечания уходят воркеру. Лимит попыток кода+ревью: `max_code_attempts`. Провал → `tests_red` / `review`.
5. **Слияние** (последовательно): `merge --no-ff` в интеграционную ветку → `full_test_command`.
   Конфликт → `merge_conflict`. Регрессия (полный набор был зелёным, стал красным) → откат слияния, `regression`.
   Упавшая задача → зависимые получают `skipped`, независимые продолжаются.
6. Итог: статусы задач, результат полного набора, имя ветки для слияния.

Состояние: `.orch/runs/<run>/state.json` (папка `.orch/` исключена из git). `orch resume <run>` перезапускает всё, что не `done`.
В конце запуска копии упавших задач удаляются, а их наработки коммитятся в ветку `orch/<run>/<id>`.

`orch run --plan plan.json` принимает готовый план (тот же формат), пропуская опрос и планирование.
Невалидный план отклоняется до начала работы.

## Режим чата `/orch`

Навык Claude Code (`orch/skill/SKILL.md`, ставится командой `orch install-skill` в `~/.claude/skills/orch`,
только ручной вызов: `disable-model-invocation: true`). В чате Claude ведёт опрос, готовит окружение
(воркеры не запускают команды), пишет план в `.orch/plans/*.json`, показывает его, после согласия запускает
`orch run --plan … --yes` в фоне, пересказывает итог и вливает ветку только по согласию.
`orch init` готовит новую папку: git, `.gitignore`, `orch.toml`, первый коммит. Существующую историю не трогает.

## Конфиг `orch.toml` (необязателен)

```toml
[models]
brain = "claude-fable-5-1"
worker = "claude-opus-5-5"
[run]
parallel = 3
max_test_attempts = 2
max_code_attempts = 3
[tests]
full = "npm test"        # иначе автоопределение: package.json → npm test, Python-проект → python -m pytest -q
timeout = 900
[worktree]
link = ["node_modules"]  # неотслеживаемые папки, которые подключаются в каждый worktree ссылкой; по умолчанию найденные из node_modules/.venv/venv
setup = ""               # команда подготовки worktree, например "npm ci"
```

## Критерии готовности

- Все тесты `tests/` зелёные на Windows (фейковая модель + настоящий git).
- Живой прогон на игрушечном проекте через настоящий `claude -p` проходит до зелёного.
